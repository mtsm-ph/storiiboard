# Brief 6.19, review fixes

Read docs/briefs/6.19-mac-webkit.md first: this continues it, same rules. Fix 1 to 3.

1. **(Medium) The Menu key on Windows opens the browser's own menu over the app's.** Chromium on Windows sends the
   Menu key's `contextmenu` on keyUP; 6.19's keydown handler has by then opened the frame's menu and moved focus to
   "Add to board…", so that `contextmenu` goes to the focused button in the menu panel, which is drawn beside
   StoryboardView (AddToBoardMenu.tsx near 126), where nothing prevents it: WebView2 shows Back / Refresh / Inspect
   over the app's menu. Fix: the panel prevents `contextmenu` (`onContextMenu` → `preventDefault`), and check every
   other menu or popover panel that can hold focus when a keyboard `contextmenu` arrives (Menu.tsx, CanvasMenu
   outside the canvas if ever, ColourControl, SlashMenu, the scene heading's menu): none may let the browser's menu
   through. Test (Chromium): with the frame's menu open from Shift+F10, dispatch a `contextmenu` MouseEvent
   (`bubbles`, `cancelable`, `button: 0`) on the focused menu button and assert `defaultPrevented`.
2. **(Low-medium) An eyedropper pick now moves focus onto the frame**, in every engine: the eyedropper
   (Eyedropper.tsx near 139) prevents and stops the press in a window capture listener, so clickFocus's own
   `pointerdown` listener never runs and can't see that the press kept focus; its capture `click` listener then
   focuses the frame button under the picked image. Fix in src/ui/clickFocus.ts: a click whose press clickFocus
   never saw (no `pointerdown` reached it since the last click) counts as a press that kept focus: focus nothing.
   Make sure the normal case still works in Safari's engine (a plain click's `pointerdown` does reach it). Test:
   an eyedropper pick leaves focus on "Pick from a frame" (extend the eyedropper's existing spec with a new test,
   or e2e/macWebKit.spec.ts).
3. **(Low) The "exactly once" half of the frame-menu test proves nothing** (e2e/macWebKit.spec.ts near 204): if
   `fromKeyboard` always returned false the test would still pass. After Shift+F10 opens the menu, dispatch
   `new MouseEvent('contextmenu', { bubbles: true, cancelable: true, button: 0, clientX: 900, clientY: 700 })` on
   the frame and assert the panel hasn't moved (same left and top) and focus is still on "Add to board…". Check by
   hand that it fails when `fromKeyboard` is made to return false, then restore.
