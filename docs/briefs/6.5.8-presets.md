## What to build

1. **What a preset holds: one list in the code** (`PRESET_FIELDS` or the like, in src/core/model or
   src/core/storage), and nothing outside it can ever be saved or applied:
   - `theme` (and `themeChosen` as the theme needs it);
   - the canvas view for plans and for boards (6.5.1);
   - the board's dot grid and snap (6.5.7a);
   - `customWorkspaces` (the person's own workspaces: id, name, layout, order) and `departmentWorkspaces`;
   - `planLayers` (the plan's layer states);
   - `pdfScenePalettes`.
   A test walks every key of `Settings` and every own-key setting and asserts each is either in the list or in an
   explicit "never in a preset" list (language, weekStart, weatherUnits, planUnits, callSheetPaper, directionsApp,
   backups, backupsNextToProject, trackpad mode, profile, projectRoles, projectSelves, companies, syncNoted,
   tilesOffered, sidebarHidden, and anything else you find: name it), so a setting added later must be put in one
   list or the test fails.
2. **The record.** A `settings_preset` record under the project (the type 6.5.5 prepared): props `name`
   (cleaned as a workspace's name is: `cleanProfileText`, at most 60 characters) and `settings` (an object
   holding only the fields above, each in the form its own reader accepts). Created, renamed, replaced and
   deleted through ops (so they are in History and undoable; deleting is a trash op if records of this kind can
   go to the Trash without showing in the Trash tile as content; if not, say what you did). Listed in the 6.5
   schema version's section of docs/SBD_FORMAT.md under "Added to this version by later 6.5 milestones". It is
   read as untrusted input: every field goes back through its own defensive reader on apply (a layout through
   the shell's check), unknown fields are dropped, and a preset from a newer version applies what this version
   knows and says what it skipped. Nothing personal can be in one: assert in a test that a saved preset's JSON
   holds no name, initials, role, person id, path or company.
3. **Settings window.**
   - A save icon button in the Settings window's header ("Save preset…", with an accessible name), enabled when a
     project is open: asks for a name (default "Preset" and a number), saves the current held settings as a new
     preset in the open project. Saving under an existing name asks "Replace [name]?".
   - A "Presets" list (in the same header menu or a small Presets tab; choose what fits the window and say):
     each of this project's presets with Apply…, Rename, Delete. With no project open the list says presets live
     in a project.
   - **Apply… first shows what it will change**: a dialog listing only what differs between this computer now and
     the preset, in words ("Theme: Light → Dark", "Canvas view, plans: Paper → Dark", "Your workspaces: 3 now, 2
     in the preset (Lighting day, Scout)", "Plan layers: Grip hidden → shown"), and "Nothing would change" when
     nothing differs (Apply disabled). On Apply: the current held settings are saved as a preset named
     **"Before [name]"** in the project (replacing an earlier "Before [name]"), then the preset's settings are
     written to this computer, at once, through the same setters the Settings window uses (so the theme repaints,
     the sidebar's workspaces update, open canvases switch view). Applying replaces the held fields, the lists of
     workspaces included. One op group for the "Before" preset; the settings change itself is not an op.
   - Applying never touches anything outside the list: assert the profile, projectSelves, projectRoles, language,
     units, paper, backups and trackpad mode are byte-identical before and after.
   - Settings keep applying at once, as now; there is no "unsaved settings" state.
4. en and es through t()/tn() for every word. Keyboard reachable; the dialog traps focus as the app's dialogs do.

## Round 3 (from the review; the four rules at the top still come first; the Edit tool only)

1. HIGH. "My workspaces" travel WITH their arrangement, and applying never loses one for good.
   - A preset's `customWorkspaces` holds, for each of the person's own workspaces, its id, name, order and its
     layout AS ARRANGED: the workspace's saved layout from the layout store (storiiboard.layouts.2) if it has one,
     else its current layout, else the layout it was made from. "Before [name]" is saved the same way, so it is a
     full way back.
   - Applying sets each workspace in the preset to that layout in the layout store (current and saved; its layout
     undo cleared), adds the ones this computer lacks, and removes the ones the preset lacks (their layouts go
     with them: they are in "Before [name]").
   - Built-in workspaces' and department workspaces' layouts are never in a preset and never touched by apply: a
     department workspace taken off the sidebar by a preset and put back later still has its layout.
   - The lists say this truthfully: custom workspaces' layouts travel inside `customWorkspaces`; every other
     layout in storiiboard.layouts.2 is never in a preset. The "nothing outside the list changes" test also
     compares storiiboard.layouts.2 for every workspace that is not a custom one.
   - Tests: the reviewer's probe (make "Lighting day", rearrange and Save layout, apply a preset with no
     workspaces, apply "Before …": the saved arrangement is back exactly); a preset saved on one "computer"
     (settings and layout store) and applied on a fresh one gives the arranged layout; built-in and department
     layouts byte-identical before and after.
2. MEDIUM. A preset is a file from other people: bound and clean it on read (settingsPreset.ts), before the
   preview and before anything is written.
   - The whole `settings` value serialised over 512 KB: the preset is unreadable ("This preset is too large to
     read"), nothing applies.
   - Layouts are rebuilt clean, not passed through: only the known keys of each node; depth at most 16; at most
     64 stacks and 200 tiles in all; a tile at most once; only tile ids this version knows. The check is
     iterative or depth-limited so nothing recurses on untrusted depth.
   - `planLayers`: only the rows this version knows (ROW_ORDER), each `{show, locked}` checked; unknown rows are
     not written to this computer from a preset (the local "keep unknown rows" rule still applies to the
     person's own settings).
   - Tests: a 1 MB junk row; a 50,000-deep split; a stack of 200,000 repeated tiles; extra keys on nodes: none
     throws, none is written; the Apply window renders.
3. MEDIUM. A field any part of which this version can't read is left exactly as it is on this computer and named
   in the preview's "Left as they are" list, never defaulted or emptied: canvasViews with an unknown view,
   boardGrid with a non-boolean, customWorkspaces if ANY workspace in it is unusable (so applying can never
   delete someone's workspaces because of a newer version's tile), departmentWorkspaces with an unknown
   department, theme outside the union, planLayers with a bad row. Rewrite your test that asserted `board: 7`
   becomes 'paper' (your own test) and make docs/SBD_FORMAT.md say exactly this.
4. "Before [name]" names: built as the Before words plus the name cut so the whole fits 60 characters; if that

5. Renaming with Enter keeps focus in the field (don't key the input by the name); the Apply window's pending

6. The notice after Apply says the way back in one line ("Applied Night. Your settings before are saved as Before
   Night.").
7. The storage-key scan also catches keys with `_` and other characters (match up to the closing quote), and
