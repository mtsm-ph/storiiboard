## What to build

1. **Reading EXIF, in Rust, on this computer.** A function in a new src-tauri/src/exif.rs (kamadak-exif) that,
   from a photo's bytes, returns: the time it was taken (`DateTimeOriginal`, with `OffsetTimeOriginal` when the
   file has it; else `DateTime`), and its GPS latitude and longitude as decimal degrees (with their N/S/E/W
   references applied). Anything missing, malformed or out of range is "not there", never an error: a photo with
   no EXIF imports exactly as today. The bytes are untrusted: a size cap before parsing (the import's own cap),
   no panic on a crafted file (tests with truncated and garbage EXIF). Nothing is logged, ever (a place is
   personal data). Exposed as a command the page calls with the bytes it is importing (or folded into the
   existing import command if photos already come through Rust: say which), added to the contract test. In the
   browser dev build (`?files=memory`), a stand-in the tests can feed (the pattern the time-zone lookup uses).
   - JPEG is the format to support and test. HEIC: kamadak-exif can read EXIF from a HEIF container; wire it so
     a HEIC photo that the app can already import (where the webview decodes it) gets its EXIF read the same
     way, and say plainly what happens today when a HEIC is dropped on a location on each system. No decoding
     work, no conversion: HEIC pictures on Windows wait for Kevin's own files.
2. **Stored on the photo's record** (a location's photo is a `media` record: confirm), all optional:
   `taken_at` (the wall-clock time as the camera wrote it, `YYYY-MM-DDTHH:mm:ss`, no zone), `taken_offset`
   (`+02:00`, only when the file says), `gps_latitude`, `gps_longitude` (numbers, every decimal kept). Written
   in the same op group as the photo's import. Read through one reader in src/core/model that refuses odd values
   (reads as not there). History's summary treats the GPS as private, as a location's coordinates are (6.5.5).
3. **The schema version.** New props, so a new schema version, 16, made here for this milestone AND for the 6.6
   build-mode milestones that follow (one version; docs/SBD_FORMAT.md gets "Schema v16" listing this brief's
   props and a list "Added to this version by later 6.6 milestones"). A migration file with no statements, as
   015 is. **Existing test this brief changes:** src/core/storage/migrations/015_canvas_polish.test.ts: its
   "is the newest schema…" assertion (`expect(SCHEMA_VERSION).toBe(15)`) becomes "015 is migration 15" (the
   migration's own version), its title no longer says "newest", and any pinned 15 for the version a file reaches
   after upgrading becomes `SCHEMA_VERSION`; the newest-version assertion moves to the new 016 test. Nothing
   else in it changes. If any other existing test pins 15 as the newest (grep src, e2e), stop and report it.
4. **In the Locations tile**, on each photo that has them: its date and time ("Taken Nov 3, 2026, 16:42") and,
   if it has GPS, its place to 5 decimals (through `formatCoordinates`, which 6.25 sets to 5; if it still shows
   4 on this branch, use it as it is). And one action per such photo, **"Use this photo's place and time"**
   (a button with that name; keyboard reachable; en and es through t()):
   - **Place:** if the photo has GPS, the location's coordinates become the photo's, exactly as pasted
     coordinates do (`pasteCoordinatesChanges`: one op, the pin moves, the zone is found offline as a moved pin's
     is, `map_name` becomes the coordinates' text). No request to Nominatim or anywhere, ever: assert it.
   - **Time:** the photo becomes the location's light reference: the location stores `light_photo_id` (that
     media record's id; one per location; choosing another photo replaces it; "Clear" removes it). Both in ONE
     op group, one undo.
   - A photo with a time but no GPS sets only the time (the button says "Use this photo's time"); with GPS but
     no time, only the place ("Use this photo's place"). A photo with neither has no button.
5. **The sun on a plan.** When the sun path's place comes from a location (the reading rule's source "From the
   location") and that location has a light reference photo with a time:
   - the sun path's settings (the Selection tile) show "Light reference: [photo's name], Nov 3, 16:42" and a
     switch **"Show the sun at the photo's time"** (stored on the sun path item: `at_photo: true`; an op);
   - with the switch on, the sun is drawn for the PHOTO's date, and a marker on the path shows where the sun
     stood at the photo's time (in the location's zone; if the photo carries its own offset, that instant),
     with a label of the time; the item and the compass say "From the photo: Nov 3, 16:42" as the source of the
     date, in place of "From the shoot day". It is the person's explicit choice, so here the photo wins over
     the shoot day; with the switch off, everything is exactly as before.
   - The reading rule (sunSources.ts) gains this as one more source with its name; its result type (what
     `get_plan` will return) carries it; with no reference photo or the switch off, its result is exactly
     today's (assert with `toEqual` on the existing cases).
   - If the photo is trashed or its time unreadable, the switch shows off and says why; nothing throws.
   - Printing: the plan prints what it shows (the marker and the source line in the legend where the sun's
     source prints today; if the sun's source doesn't print today, print nothing new and say so).
6. **EXIF never leaves in an export.** The stored picture is re-encoded on import, so it should carry none:
   prove it with tests: (a) the stored bytes of an imported photo that had EXIF contain no EXIF segment and none
   of the GPS values; (b) every export that can carry a location's photo (the call sheet PDF if it shows one,
   the lossless JSON export, a board or deck that shows the picture, Collect/.sbdpack if it exists): the photo's
   bytes there have no EXIF. The JSON export is lossless by rule, so it DOES carry the four props on the record
   (that is the project, not an export for others): say so in docs/SBD_FORMAT.md. The CSV exports carry none of
   them.
7. docs/SBD_FORMAT.md: the four props on a location's photo, `light_photo_id` on a location, `at_photo` on a sun
   path, all under Schema v16; a line that a photo's place and time count as contact details for what an
   assistant may read (Phase 7), and that EXIF is read on this computer and never sent anywhere.
