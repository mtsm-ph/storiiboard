# Brief 4.3: sun times, in the location's time zone

For the builder (.claude/agents/builder.md). Written by the main session, Nov 10, 2026. Read CLAUDE.md first; its
Safety section comes before this brief. You start with no other context: everything you need is here or in the files
named.

## Goal

Each location on a call sheet shows the day's sunrise, sunset, golden hours and blue hours, worked out offline from
the location's place on the map (its `latitude` and `longitude`, picked from the address search in 3.4) and the day's
date, in the location's time zone (docs/PHASE4_DECISIONS.md, decisions 3 and 7; CLAUDE.md, "Call sheets").

The call sheet is the Call sheet tile (src/features/callsheets/, its data from src/core/model/callsheet.ts), built in
4.1 and 4.2. Read both before starting.

## Decisions that apply

- **Sun times: SunCalc**, the npm package `suncalc`, pinned exactly at `2.1.1` (published Oct 5, 2026; at least two
  weeks old, as CLAUDE.md requires; 2.1.2 and 2.1.3 are newer than two weeks, don't take them). It ships its own types
  (index.d.ts); no @types package. Install it with `npm install --save-exact suncalc@2.1.1` (this brief names it, so
  you may install it).
  - Golden hour: the sun between 6° above and 4° below the horizon; morning (rising through −4° to +6°) and evening
    (+6° down to −4°). Blue hour: 4° to 6° below the horizon, morning and evening (Kevin, Nov 9). Add the angles with
    SunCalc's `addTime` once, in one module, and say in a comment why (the angles are Kevin's, not SunCalc's own
    golden hour, which ends at the horizon).
  - Read the times for the day's date at the location, so they're the right day there: ask SunCalc for noon in the
    location's time zone on that date (not noon UTC, which is the wrong day for places far from Greenwich).
  - Where the sun doesn't rise or set that day (polar day or night), SunCalc gives invalid dates: show "Sun up all
    day" or "Sun down all day" in place of the times, and leave out any golden or blue hour that doesn't happen.
  - A location without a place on the map shows "Pick the address on the map for sun times" (muted), pointing to the
    Locations tile's Search address; nothing is guessed from the address text.
  - Times as HH:MM (24-hour, as the rest of the sheet; JetBrains Mono), each range as "06:12–06:48".
- **The location's time zone: tzf-rs on the Rust side** (Kevin, Nov 10; replaces @photostructure/tz-lookup, which is
  not installed). Offline, from the coordinates; never a lookup service.
  - Cargo: `tzf-rs = { version = "=2.1.3", default-features = false, features = ["bundled"] }` (MIT, Oct 11, 2026;
    `default-features = false` leaves out its command-line `clap`). Its data crate `tzf-dist` must resolve to
    `0.0.2026-e` (Oct 11; MIT and ODbL-1.0, the OpenStreetMap data): after adding tzf-rs run
    `cargo update -p tzf-dist --precise 0.0.2026-e` in src-tauri and check Cargo.lock has it (0.0.2026-f is Nov 1,
    newer than two weeks). geometry-rs resolves to 0.5.1 (Jul 28), fine.
  - tzf-rs 2.1.3 declares `rust-version = 1.88`; src-tauri/Cargo.toml says `rust-version = "1.85"`. Raise it to
    `"1.88"` (CI uses stable; this computer has 1.99). Don't change anything else in Cargo.toml.
  - If tzf-rs doesn't build cleanly here on Windows (`cargo build` and `cargo test` in src-tauri, and
    `cargo clippy --all-targets -- -D warnings` if the repo's CI runs clippy: read .github/workflows/ci.yml), stop
    and report: Kevin wants to be told before any fallback.
  - A new src-tauri/src/timezone.rs: one finder built once, lazily, on first use (`std::sync::OnceLock`; building it
    takes a while and memory, so never at startup), and `#[tauri::command] time_zone_at(latitude, longitude) ->
    Option<String>`, the IANA id ("America/New_York"), None for NaN, out-of-range coordinates, or a point it can't
    place. Register it in src-tauri/src/lib.rs. Rust tests: New York, Madrid, Mexico City, a point at sea (whatever
    tzf gives there, e.g. an `Etc/GMT…` zone, is acceptable; say in the test what it gives), out-of-range input.
  - Its credit: tzf's data comes from timezone-boundary-builder, from OpenStreetMap (ODbL). Under the location's Time
    zone field, a small credit line the way `location.mapCredit` sits under Search address ("Time zones from
    timezone-boundary-builder. Data © OpenStreetMap contributors, ODbL."), in en and es. The licence texts of tzf-rs
    (MIT) and SunCalc (BSD-2-Clause) go with the release's third-party notices (Phase 8); the main session notes that in
    docs/PLAN.md.
  - The page's bridge: src/app/timeZone.ts calls the command; its browser fallback (end-to-end tests, `?files=memory`)
    returns this computer's zone (`Intl.DateTimeFormat().resolvedOptions().timeZone`), so tests are deterministic
    when Playwright sets a `timezoneId`.
- **Editable on the location:** a new location prop `time_zone` (an IANA id). The Locations tile (src/features/
  locations/LocationsTile.tsx) gets a "Time zone" field below the address: a Select whose first option is "From the
  map: America/New_York" (the looked-up zone; "From the map: none yet" without a place), then every IANA zone
  (`Intl.supportedValuesOf('timeZone')`, sorted). Choosing the first option unsets the prop. One edit. Unknown or odd
  values read as unset (validate with `Intl.DateTimeFormat(undefined, { timeZone })` in a try). Document `time_zone`
  in docs/SBD_FORMAT.md's "Location props (3.3)" (additive, no schema number, as `full_view`).
  - A new address that takes off the map place (`unpinnedBy` in src/core/model/location.ts) leaves `time_zone` as it
    is: it was set by hand on purpose.
- **On the call sheet:** each location in its section gets a "Sun" block: Sunrise, Sunset, Golden hour (morning and
  evening ranges), Blue hour (morning and evening ranges), and the zone the times are in ("Times in America/New_York").
  Golden hour is marked with Burning Flame (the golden-hour token; ink text on it) and a second cue (the words
  themselves), never the accent (design/DESIGN.md). The day section's crew call and wrap are wall-clock times as
  typed, shown as they are; add "Times in <zone>" under them, from the day's first location (or none).
  - The computation is a pure function in a new src/core/model/sunTimes.ts: `sunTimes(date, latitude, longitude,
    timeZone)` returning HH:MM strings or the up-all-day / down-all-day state, so it's tested without the page.
    Format with `Intl.DateTimeFormat` and `timeZone`, never by adding offsets by hand (summer time).
  - The zone a location uses: its `time_zone` when set and valid, else the looked-up zone, else this computer's, said
    as "Times in this computer's time zone" so it's not mistaken for the location's.
- **Not in 4.3:** the golden-hour-at-midday check is 4.8's. Weather is 4.4's.
