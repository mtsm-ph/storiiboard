## The rule (Kevin, Nov 16)

"Wherever the app reads a sort key (Bring to front and Send to back on a plan or a board, adding or reordering a
setup, the moodboard path), an unreadable one from an odd imported file never makes it throw."

A stored `sortKey` (and any stored prop used as an order key) can be any string: an imported or hand-edited file
may hold one `keyBetween` (src/core/ops/order.ts) refuses, or two out of order. `keyBetween` keeps its contract
and its tests. What changes is every caller that hands it a key read from the records.

## What to build

1. Move the guarded helpers to src/core/ops/order.ts (pure functions over keys, no records: e.g.
   `keyAfterStored(last, readable)` / `keyBetweenStored(before, after, last)`; keep the records-reading
   `keyAfterLast`/`lastReadableKeyUnder` in src/core/model/plan.ts or move them beside `lastKeyUnder`'s home, your
   choice, one home only) and re-export or re-import so 6.22's call sites keep working unchanged in behaviour.
2. Go through EVERY non-test call of `keyBetween(` in src (about 62 in 31 files; `grep -rn "keyBetween(" src`).
   For each: do its arguments come from stored records (directly or through a "last key" reader)? If yes, it goes
   through a guarded helper so it can't throw:
   - "after the last" / "before the first": fall back to after the last readable sibling key (or
     `keyBetween(null, null)` when none is readable), as 6.22.
   - "between two stored keys" (reorders: frames and scenes on the storyboard, setups, shoot days, gear, people,
     locations, pages, sections, board items, attachments, call sheet rows, whatever the list is): when either key
     is unreadable or the two are out of order, the edit still gives the order the person asked for. Do it the way
     6.22 round 3 did for marks: write the list's whole sequence as shown with the move applied (fresh keys for
     those siblings, same op group). If a call site can't see its siblings, say so and use the smallest change
     that still can't throw.
   - src/ui/canvas/zOrder.ts `sortKeysFor` (Bring to front, Send to back, forward, backward on boards and plans):
     same rule; this brief allows changing that file, nothing else in src/ui/canvas.
   - Keys made in the same call (a chain from a key the function itself just made) need nothing.
   - Migrations (src/core/storage/migrations) are frozen: leave them, but say whether one can throw on an odd key.
3. A sound file gets exactly the keys it got before at every call site, and no per-edit path scans the records
   more than before (the scan-count tests in recordIndex.test.ts and gearOnDay.test.ts must pass untouched).
4. Also report (read only, don't change): where a file comes in (opening an .sbd in src/core/storage, JSON import,
   .sbdpack), is a record's sort key checked or repaired? One paragraph, so Kevin knows whether an odd key can
   arrive at all and by which doors.
