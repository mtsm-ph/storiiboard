# Brief 6.14: a contract test between the page and Rust; the test drivers refuse what Rust refuses

Read CLAUDE.md first (Safety before all), then docs/DESKTOP_GAPS.md ("Why these bugs get through", B3, and "The
cheapest cover", item 2). Kevin approved item 2 and B3 on Nov 14. No new dependency.

## Why

#144 found that an export had failed to save in the desktop app since Phase 2: the page and Rust disagreed, and
every test mocks `invoke` or uses a browser stand-in. Only src/features/export/exportExtensions.test.ts (read it:
it is the pattern) compares the two sides.

## What to build

### 1. The contract test (Vitest, node environment, reads source files as text; suggest src/app/tauriContract.test.ts)

- **Rust's side:** the commands registered in src-tauri/src/lib.rs (`tauri::generate_handler![…]`), and for each
  its `#[tauri::command]` function's parameters, found in src-tauri/src/**/*.rs. Leave out the parameters Tauri
  injects itself (`AppHandle`, `Window`/`WebviewWindow`, `State<…>`, `tauri::ipc::Channel` and the like: decide from
  the type) and note `Option<…>` parameters as optional. Tauri turns a Rust `snake_case` parameter into a
  `camelCase` argument unless the command says `rename_all`: handle both, from the attribute.
- **The page's side:** every `invoke(` call in src (not tests): the command name and the keys of its argument
  object. Calls go through wrappers in places; find every way the page reaches `invoke` (search for `invoke(`,
  `invoke<` and any helper that takes a command name) and cover them. A call whose name or argument object isn't a
  literal the test can read must be listed by file in an explicit allowlist inside the test, each with a reason,
  and the test fails on any unlisted one, so a new unreadable call can't slip by.
- **It fails when:** a call names a command that isn't registered; a registered command is never called (an
  allowlist with reasons for any that are called only from Rust or kept on purpose); a call passes a key Rust
  doesn't take; a call leaves out a parameter that isn't an `Option`. Each failure message names the command, the
  file and the key.
- **Events:** the audit notes that event names (drag-drop, `opened-files` and others) are "shared only as text".
  Add the same check for them: every event the page listens to (`listen(`, `once(`, `onDragDropEvent` and similar)
  that Rust emits by name (`emit(`, `emit_to(`) must match a name in Rust, and the reverse; Tauri's own built-in
  events go in a short allowlist with a reason.
- **Prove it bites:** the test file includes a few unit cases of its own parsers on small inline strings (a command
  with injected parameters, an `Option`, `rename_all`, a multi-line signature), and you check by hand, then undo,
  that renaming one argument key in a real call makes the test fail. Say which in the report; `git diff` on that
  file must be empty afterwards.
- Not return shapes: out of scope (the audit says so). Don't try.

If the test finds a real mismatch in today's code, that is a desktop bug: fix the page or Rust (small and certain
only), add it to the report; otherwise stop and report.

### 2. B3: the two test drivers refuse what Rust refuses

src-tauri/src/sbd.rs refuses (a) a query whose result contains bytes (a blob column in a row) and (b) a blob read
of a column that isn't a blob. The drivers the tests use, src/core/storage/memoryDriver.ts and nodeDriver.ts,
return a value instead, so code that did either would pass every test and fail only on the desktop.

- Read sbd.rs for the exact rule and error in each case (which commands, which SQLite types count, what NULL does)
  and make both drivers refuse the same inputs, with an error that says the same thing. Match Rust exactly on the
  edge cases (NULL, an empty blob, text in a blob column); where Rust's behaviour is unclear from the code, write
  a Rust unit test in sbd.rs that pins it and mirror that.
- Tests: for each driver, a test per rule (the existing driver test files run the same cases over both drivers:
  extend that). If Rust has no unit test of the refusals, add them in sbd.rs's tests so both sides are pinned.
- If making the drivers strict makes any existing test fail, that test's code path would fail on the desktop: it
  is a finding. Fix the app code if small and certain; otherwise stop and report. Never loosen the driver or the
  test to get through.
