# Brief 6.13: the end-to-end tests run under the app's real content security policy

Read CLAUDE.md first (Safety before all), then docs/DESKTOP_GAPS.md ("Why these bugs get through", A1, and "The
cheapest cover", item 1). Kevin approved item 1 on Nov 14.

## Why

The installed app's page runs under the CSP in `src-tauri/tauri.conf.json` (`app.security.csp`). The end-to-end
tests' page (Vite's dev server, started by Playwright with `STORIIBOARD_E2E=1`, see vite.config.ts and
playwright.config.ts) runs under none, so anything the CSP refuses is found only in an installer. That is how A1
(a company logo decoded with `fetch('data:…')`, refused by `connect-src`) shipped; 5.12 fixed it and added
src/app/cspFetch.test.ts, which lists every `fetch(` in src.

## What to build

1. **For the test server only** (`STORIIBOARD_E2E === '1'` in vite.config.ts; everyday `npm run dev` and `tauri dev`
   are unchanged), Vite sends a `Content-Security-Policy` response header on the page: the string read from
   src-tauri/tauri.conf.json at server start (never a copy typed into vite.config.ts), plus only what the test build
   alone needs. A header, not a `<meta>` tag.
2. **The additions live in one small module** (suggest `scripts/e2eCsp.ts` or next to vite.config.ts, importable by
   both Vite's config and Vitest), as a list where each entry names the directive, the source added and why. Expected
   entries, and nothing else without a reason you can show:
   - `'wasm-unsafe-eval'` for scripts: the tests keep projects in sql.js (WebAssembly; src/app/fileAccess.ts), which
     the desktop app never loads.
   - whatever Vite's dev page itself needs that a built app doesn't. React's refresh preamble is an inline module
     script that `@vitejs/plugin-react` puts in index.html while serving: the CSP has no `'unsafe-inline'` for
     scripts and must not gain it. Handle it narrowly: a hash or a nonce for that one script, or serve the preamble
     as a file from the server, or leave the preamble out for the test server (hot reload is already off there). Pick
     the smallest that works in both Chromium and WebKit and say which in the report.
   - The CSP has no `script-src`, so scripts fall under `default-src 'self'`. If you add a `script-src` directive to
     carry the additions, it must start from what `default-src` gives (`'self'`), never wider.
3. **Never loosen a directive to get a test through.** When a test fails under the CSP, decide which it is:
   - the app itself does something the installed app would refuse (a real desktop bug, like A1). If the fix is small
     and certain (as 5.12's was: decode without `fetch`), fix the code and add a test; otherwise leave it failing,
     stop, and report the test's name, the violated directive and the blocked address;
   - or it is something only the test build does (sql.js, Vite's dev client, the in-page stand-ins for Rust). Then
     add one entry to the additions list with its reason.
   Report every such case either way.
4. **Tests to add**
   - Vitest (`src/app/e2eCsp.test.ts` or beside the module): the header's value is tauri.conf.json's CSP with exactly
     the listed additions and nothing removed: for every directive in tauri.conf.json, every source it lists is still
     in the header; the only extra sources are the list's; no `'unsafe-inline'` or `'unsafe-eval'` for scripts; no
     `*`. So a later loosening shows up as a failing test with a diff to justify.
   - Playwright, in e2e/shell.spec.ts (new tests only; existing tests there stay as they are): (a) the page's
     response carries the `Content-Security-Policy` header and it contains tauri.conf.json's `connect-src` text;
     (b) the policy is live: in the page, a `fetch('data:text/plain,x')` is refused (it rejects, and a
     `securitypolicyviolation` event names `connect-src`). This is A1 in miniature.
   - Find out how the suite treats console errors and CSP violations today (search e2e/ for `console`, `pageerror`
     and fixtures). A CSP violation anywhere in any test must fail that test or be listed by name in your report: if
     nothing fails a test on a violation today, add a `securitypolicyviolation` listener through the suite's shared
     setup (the helper or fixture most specs already use), failing the test with the directive and blocked address.
     Do not rewrite specs wholesale to do it; if it can't be done without touching every spec, stop and report the
     options.
5. **Prove it would have caught A1.** Temporarily change `logoFile` in src/app/company/companies.ts back to decoding
   with `fetch(dataUrl)`, run the company-logo end-to-end test, and record that it fails with the CSP message. Then
   restore the file exactly (`git diff src/app/company/companies.ts` must be empty) and say so in the report.

## What not to touch

- src-tauri/tauri.conf.json's CSP itself. If you believe the real CSP must change, stop and report.
- Existing tests and assertions (builder.md: never weaken, skip or delete one). Screenshot baselines.
- .github, .claude. No new dependency.

## Checks to run (foreground, one at a time)

- `npx tsc --noEmit` and `npx eslint .`
- `npx vitest run`
- The whole end-to-end suite in Chromium: `npx playwright test --project=chromium --workers=4`. A foreground
  command here is limited to 10 minutes, so run it in shards: `--shard=1/8` to `--shard=8/8` (more shards if one
  doesn't fit). Each shard rewrites test-results/e2e.json: note the failed and flaky test names from every shard's
  own output before starting the next. WebKit is not installed in this container; the Mac's CI run covers it.
- Reference: test-results/ may be emptied by runs. The main session ran the same suite on the untouched tree and
  will compare your failures with its list; a test that fails for you, report by name with its error, whatever you
  think the cause is.
- Rust is untouched: no cargo commands.
