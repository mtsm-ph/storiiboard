## App fixes (a person on the Mac app would hit these)

**E. A board's right-click menu closes before its command runs.** In Safari's engine a clicked button takes no
focus; the canvas menu (src/ui/canvas or src/features/moodboards: CanvasMenu.tsx, around its `onBlur` → `onClose`)
closes on the blur that the mousedown causes, before `click`. Fix: the menu must not lose focus to a mousedown
inside itself (`onMouseDown` → `preventDefault` on the panel, or close on blur only when focus leaves to outside
the panel: `relatedTarget` not inside, and never on a mousedown inside). Keyboard use, Escape, and a click outside
closing it stay as they are. Check every other menu and popover in src/ui (Menu.tsx and anything with the same
onBlur pattern) for the same fault and fix each the same way; list them.
Tests it accounts for: boardMedia "Copy from the context menu…", moodboard "opens a context menu…", sections "the
context menu selects a section's contents". Add a Chromium-runnable test of the mechanism: with the menu open, a
`mousedown` on a command that moves focus nowhere (dispatch it so the button does not take focus) must not close
the menu before `click`.

**F. Shift+F10 / the Menu key on a storyboard frame opens nothing on a Mac.** StoryboardView.tsx (near line 496)
relies on the browser's own `contextmenu` event for the keyboard; Mac WebKit sends none for Shift+F10. The board
canvas already handles the keys itself (src/ui/canvas/Canvas.tsx near 1143, and ignores the keyboard's own
`contextmenu` near 1454): do the same for frames and scene headings on the storyboard, and anywhere else a context
menu is offered only through `onContextMenu` on a focusable element (search src for `onContextMenu`; list each and
whether it needed the fix). The menu opens at the focused element, exactly once (not twice in browsers that also
send `contextmenu`).
Tests: liveCards "Add to board… from a frame's context menu…" (its Shift+F10 half), setups "the frame menu from
the keyboard…".

**B. A clicked button isn't focused in Safari's engine**, so "focus returns to the button that opened it" and
similar are wrong on the Mac: after Cancel in a question, focus goes to nothing. Two places already patch it by
hand (ThemeImageWell.tsx near 86, InspectorView.tsx near 801). Do it once: beside `installTabWrap`
(src/ui/tabWrap.ts, installed in the desktop and dev builds), a capture-phase listener that, on a pointer click
(`event.detail > 0`) of an enabled `button`, `[role=button]`, `summary` or `a[href]` (the nearest such ancestor of
the target) that isn't already the active element, focuses it with `{ preventScroll: true }`. It must not steal
focus from a text field the click handler itself focuses (run in capture, before the handlers), must not fire for
keyboard clicks, and must not interfere with E's menus (a menu command's mousedown still doesn't blur the menu).
Remove the two hand patches only if they become dead code and their tests stay green; otherwise leave them.
Tests: a11ySweep "Tab goes round the page and a window…", callSheets "who is on the day…", emptyTrash (3), player
"grabs the frame showing…", video "Settings → Storage…". Add a Vitest or Chromium test of the listener with a
button made unfocusable-by-click (`mousedown` default prevented, as Safari behaves).

**H. A Library drag that was cancelled still places an item** (unproven; inferred): after Escape or a context menu
cancels a drag from the Library, the later mouse release still sends `click` to the Library's button, which places
the item (LibraryTile.tsx near 292 and 505; the press is ended on a 0 ms timer). Fix: a cancelled drag swallows
the pointer click that ends it (a ref set in `cancel()`, cleared on the next `pointerdown`; `onClick` ignores a
pointer click, `event.detail > 0`, while it is set). Keyboard placing is untouched.
Tests: library "a drag cancelled by Escape or by the system…", "a drag ends when its button is found up…".

## Test arrangement fixes (the test drives the page in a way a Mac doesn't; assertions stay word for word)

**G.** e2e/decks.spec.ts near 218 and 224 press `Control+Alt+KeyP`; on a Mac the app wants ⌘⌥P (presentKey.ts).
Use the spec's own platform modifier (`mod`, as the rest of that spec does).

**C. Playwright's "Desktop Safari" draws at pixel ratio 2**, Chromium's device at 1. The picture-size rule
(src/core/media/decoded.ts `levelFor`) multiplies by the pixel ratio, by design (brief 5.7), so thresholds the
specs compute for ratio 1 ("640 screen pixels") are met at half the zoom. In e2e/boardMedia.spec.ts and
e2e/planUnderlay.spec.ts add `test.use({ deviceScaleFactor: 1 })` at the top with a comment saying why (the
numbers in this spec are for a pixel ratio of 1; the rule itself is unit-tested for 2: check that it is, in the
Vitest tests of `levelFor`, and add the case if not).

**D. Pointer positions land a fraction off in WebKit at ratio 2** (unproven): on boards, y lands 1 px above what
the spec asks; on plans, x 0.81 px left. Likely cause: at ratio 2 the layout has half-pixel edges (the 1.5 px
rules), and the specs' `origin()`/`world()`/`screen()` helpers assume whole CSS pixels while WebKit delivers whole
`clientX/Y`. First read those helpers (e2e/moodboard.spec.ts, connectors.spec.ts, sections.spec.ts, plan.spec.ts,
planUnderlay.spec.ts and any shared helper) and the canvas's pointer maths (src/ui/canvas/Canvas.tsx near 500) and
decide whether the app's maths is right for a fractional rect and fractional pointer positions (it reads the
pointer against its own `getBoundingClientRect()`: say whether anything rounds). If the app is right, add the same
`test.use({ deviceScaleFactor: 1 })` with the same comment to the canvas specs whose arithmetic assumes whole
pixels: moodboard, connectors, sections, plan, planUnderlay (already above) and any other spec that drives a
canvas by computed positions. If the app's maths is wrong for fractional positions, fix the app instead and say
so. Tests: connectors (7), moodboard (5), sections (8), planUnderlay (2), and probably plan (2).
