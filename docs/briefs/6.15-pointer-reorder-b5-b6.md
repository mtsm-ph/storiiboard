# Brief 6.15: deck pages reorder by pointer events; no HTML5 drag and drop in the app; B5 and B6

Read CLAUDE.md first (Safety before all), then docs/DESKTOP_GAPS.md (B1, B5, B6). Kevin, Nov 14: fix B1 now
without waiting for his look; then a lint rule or test that fails on HTML5 drag and drop anywhere in the app, since
Tauri's file drop switches it off on Windows; fix B5 and B6 now, small.

## Why (B1)

The desktop window has Tauri's file drop on (`dragDropEnabled`, needed for pictures dropped from Explorer or
Finder). On Windows that switches HTML5 drag and drop off inside the page: `dragstart`, `dragover` and `drop` never
fire for something dragged within the app. src/features/moodboards/PagesPanel.tsx reorders a deck's pages with
HTML5 drag and drop, so in the Windows app the drag does nothing (Move up and Move down still work). The tests run
in a browser, where it works, so no test sees it.

### 2. The rule: no HTML5 drag and drop anywhere in the app

First list every use in src (not tests): `draggable` on a DOM element, `onDragStart`, `onDrag`, `onDragEnd`,
`onDragEnter`, `onDragOver`, `onDragLeave`, `onDrop`, `addEventListener('drag…'/'drop')`, `dataTransfer`,
`DragEvent`. Today's files: src/app/theme/ThemeImageWell.tsx, src/app/theme/OnboardingDialog.tsx,
src/features/birdseye/plan/PlanTile.tsx, src/features/locations/LocationMap.tsx,
src/features/storyboard/useBoardDrops.ts, src/features/storyboard/FrameImage.tsx,
src/features/moodboards/PagesPanel.tsx, src/features/moodboards/BoardView.tsx. Konva's own `draggable` prop on
canvas nodes (react-konva components such as `<Group draggable>`) is not HTML5 drag and drop and stays.

Sort each use into one of three kinds and put the list in your report:
- **(a) A drag that starts inside the app** (a `draggable` DOM element, `onDragStart`, `dataTransfer.setData`):
  broken in the Windows app. Convert it to pointer events as in part 1, with a test. If one is too big to do
  safely in this brief, leave it, stop converting, and report it with what it would take.
- **(b) Receiving files dropped from the operating system** in the browser build only, where the desktop app gets
  the same drop through Tauri's drag-drop event instead. Allowed, but only in files named in the rule's allowlist,
  each with a comment saying where its Tauri counterpart is. If a file receives OS drops through HTML5 only, with
  no Tauri path, the desktop app can't do it at all: report it as a finding (don't build the Tauri path here).
- **(c) Anything else**: report.

Then the rule itself, so a new use fails `npm run lint` or `npm test`:
- Prefer an ESLint rule in eslint.config.js built from what ESLint already has (`no-restricted-syntax` selectors
  for the JSX attributes on lowercase (DOM) elements and for `dataTransfer`/`DragEvent`, `no-restricted-properties`,
  `no-restricted-globals`), with the message "HTML5 drag and drop is off inside the Windows app (Tauri's file drop):
  use pointer events (src/…/the hook)". The allowlist for kind (b) is an `overrides`/files block in
  eslint.config.js listing those files and allowing only the receiving handlers (`onDragOver`, `onDragEnter`,
  `onDragLeave`, `onDrop`, reading `dataTransfer.files`/`items`/`types`), never `draggable`, `onDragStart` or
  `setData`.
- If ESLint's built-ins can't tell a DOM `draggable` from Konva's, use a Vitest test that reads src as text
  instead (as src/app/cspFetch.test.ts does for `fetch(`), with the same allowlist. No new dependency, no new
  ESLint plugin.
- Prove it bites: add a `draggable` attribute to a `<div>` in any component, see the rule fail, remove it; say so.

### 3. B5: Show backups goes through open.rs

### 4. B6: a folder export that never commits leaves no token behind

src-tauri/src/export.rs hands the page a token for a chosen folder; an export that writes files into a folder
(PNG frames) never calls `commit()`, so its token stays in memory for the session. Read export.rs and the page's
side (src/features/export, the store that calls `export_choose_*`, `export_write`, the commit) and make the token
go away when the export ends, success or failure, without changing what the page may write while it runs: the
smallest of (i) the page ends a folder export explicitly through the existing command path, or (ii) Rust drops a
folder token when a new one is issued and caps how many can be alive. A Rust unit test that the token is gone
afterwards and can't be used again; a Vitest test on the page's side if the page changes. src/app/tauriContract
tests (6.14) and exportExtensions.test.ts must stay green: if you add or change a command, the contract test tells
you what else to update.
