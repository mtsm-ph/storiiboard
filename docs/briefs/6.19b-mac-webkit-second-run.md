# Brief 6.19b: the Mac's second whole-suite WebKit run

Read docs/briefs/6.19-mac-webkit.md first: this continues it, same rules (nothing here can be run in WebKit in this
container; no assertion is weakened). After 6.19 the Mac run went from 62 failed to 25 failed and 1 flaky (run

**1. Half a pixel (connectors 7, moodboard 4, sections 8, plan 1, planUnderlay 2).** With the pixel ratio at 1 the
error is now exactly 0.5 on y: connectors expects y -100 and gets -100.5, sections -250 and gets -250.5,
planUnderlay expects a scale of 1 within 0.005 and gets 1.0081. Reading: the specs' helpers aim at
`box.y + box.height / 2 + y`; when the canvas's height (or width) is odd, that is a half pixel; Chromium delivers
fractional pointer positions, WebKit whole ones, so the click lands half a pixel off and the world position the
app records is half a unit off. The app is right (6.19 checked its maths). Fix the arrangement, not the
assertions: each spec that aims at computed canvas positions makes its canvas's centre a whole pixel before it
starts. Do it once, in a shared helper in e2e/ (suggest e2e/wholePixels.ts) that the specs' own set-up calls after
the canvas is on screen: measure the canvas's box; if `box.x + box.width / 2` or `box.y + box.height / 2` isn't a
whole number, change the viewport by one pixel in that direction (`page.setViewportSize`) and measure again (at
most a few tries; fail the test with a clear message if it can't be reached), and also assert `box.x` and `box.y`
themselves are whole. Use it in connectors, moodboard, sections, plan, planUnderlay, and in every other spec that
aims at computed canvas positions and compares exact world values (list them and say for each whether you added
it; the ones that passed on the Mac twice can stay as they are). Chromium must be unaffected: the whole suite
stays green here. Keep 6.19's `deviceScaleFactor: 1` lines.
Also say in your report whether the app could have the same fault for a person (a pointer position truncated to a
whole pixel by the engine while the canvas centre is on a half pixel moves a click by half a screen pixel: is
anything in the app sensitive to that, such as snapping thresholds or hit tests on thin lines?). Report only.

**2. textShapes "makes a sticky note in each of its six colours" (e2e/textShapes.spec.ts near 147-163) is NEW: it

Chromium with e2e/webkitClicks.ts (the helper that presses buttons as Mac WebKit does): run that test's steps with
the helper on, find the cause, fix the app so the colour is applied in both engines, and add the case to
e2e/macWebKit.spec.ts. If it does not reproduce with the helper, say so, read ColourControl.tsx and the sticky
note's editing code for what differs when the button isn't focused at mousedown, and report what you find without
guessing a fix.

are locked, and the board says why":** as you measured, the spec's drop point is 1.5 px inside the board's scroll

those two tests (and the spec's shared drag helper if that is where it is), arrange the scroll so that both the
dragged frame and the drop point are well inside the scroll area (at least 24 px from its edges) before the drag
starts, asserting that they are; the drag's steps and every assertion after it stay word for word.
