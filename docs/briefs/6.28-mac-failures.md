## The four failures

1. **e2e/planUnderlay.spec.ts, two tests** (both existing since 6.9, both passed on the Mac on Nov 15):
   "an underlay set to scale by two clicks and "4m", a wall traced over it and measured…" (line 176:
   `expect(scaled.x + scaled.width / 2).toBeCloseTo(1, 2)` received 1.0055) and "Set scale takes its clicks
   exactly where they are, never snapped…" (line 353: expected 1.96, received 1.9655). Off by half a centimetre:
   a click that used to land on a whole pixel no longer does. **Don't touch these tests.** The suspect: 6.5.2
   made a plan's first view sit beside the tool strip (`firstViewBeside`, `middleBeside`, `PLAN_STRIP_INSET` in
   src/features/birdseye/plan/planStore.ts = STRIP_INSET 51 + RULER_SIZE 18 = 69, an ODD number of pixels, so
   the world's origin sits at a HALF pixel: 34.5). A world point on a half pixel also draws 1.5 px rules
   blurred. Fix in the product: the first view, the middle used for keyboard placing, and every fit place the
   world's origin (and a fit's result) on a whole device pixel (round the inset's half, or the resulting centre,
   to a whole pixel; say which, and why Chromium passed: its click rounding differs). Prove with a unit test
   that the first view's origin maps to a whole pixel for odd and even canvas widths and insets, and with a
   Chromium e2e check that a click at a world point's screen position reads back that world point within a
   millimetre at 100%. Say whether a SAVED view from before the fix can hold a half-pixel centre and what
   happens to it (plan views are session-only: confirm).
2. **e2e/macWebKit.spec.ts "Tab from the Hex field to outside the colour panel closes it, where the Hex field is
   the last control Tab reaches (6.5.7a)"** (a test 6.5.7a added): it waits for
   `panel.getByLabel('System colour picker')`, which does not exist on a Mac: Kevin decided Nov 15 that on a Mac
   the colour control has no picker button ("leave it; the Hex field is the keyboard way"), and the app hides it
   by user agent. This brief changes that test (named here): it must not require the picker to exist: if the
   picker is absent (count 0), one Tab from the Hex field leaves the panel and closes it; if present and focused
   after the Tab, a second Tab closes it. Keep the closing assertion. Also check the OTHER test 6.5.7a changed
   in that file ("Tab from the colour panel's last control to outside it closes the panel", which focuses
   `getByLabel('System colour picker')`): it passed on the Mac, so say why (does that describe block run with a
   user agent where the picker exists?) and whether it is sound. Run both in Chromium with Safari's user agent
   and with Chromium's own.
3. **e2e/boardGrid.spec.ts "snap to grid: a picture's and a deck page's corner end with an edge on the dots and
   their proportions kept"** (a test 6.5.7a added), line 377: after `page.mouse.click(edge.x, edge.y)` on a deck
   page's top edge, the page is not selected in WebKit (`data-selection` is `[]`). Find why from the code: where
   a deck page frame is hit (its edge only? a tolerance in screen pixels? a half-pixel edge after item 1's
   offset on boards: a board's inset is 51, also odd), and whether a PERSON on a Mac can select a page by its
   edge today (the existing deck tests select pages on the Mac: how do they click?). If it is the product (the
   edge can't be hit at some pixel alignments), fix the product (a hit tolerance that doesn't depend on
   sub-pixel luck) and keep the test as it is; if the test clicks somewhere no person would (exactly on a
   hairline), this brief allows changing only how that test selects the page (the way the existing deck tests
   do), nothing else in it. Say which, with the evidence.
4. **Flaky on the Mac, passed on retry: e2e/planLayers.spec.ts "hides, locks, dims and solos layers…"** line 163:
   the Solo click on the Camera row left `aria-pressed` false. Don't touch the test and add no retry. Read the
