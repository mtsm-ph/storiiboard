# Brief 5.7: the 500-item board, and two flaky tests

For the builder (.claude/agents/builder.md). Written by the main session, Nov 11, 2026. Read CLAUDE.md first; its
Safety section comes before this brief. You start with no other context: everything you need is here or in the files
named.

## Goal

Milestone 5.7 (docs/PLAN.md, "Phase 5 milestones"; Kevin's answers in docs/PHASE5_DECISIONS.md, decisions 4 and
12): **a board of 500 items, 150 of them pictures, pans and zooms at 60 fps** on Kevin's Mac and a mid Windows laptop,
measured with a generated board as Q2 measured a 300-frame storyboard (e2e/perf.spec.ts). Builds on 5.0 to 5.6b: read
docs/briefs/5.0 to 5.6b, then src/ui/canvas/ and src/features/moodboards/. Also find the cause of the two tests that
have failed intermittently during Phase 5 and fix it (below).

## Decisions that apply

- **Measure first.** A new e2e/perf.spec.ts test (same switch as Q2's: runs only with `SB_PERF=1`, Chromium only,
  printed numbers, budgets well above what a person notices so a slow machine doesn't flake it) builds a board of 500
  items: 150 pictures (generated in the page as Q2 does, each different, mixed sizes and aspects, through the real
  drop path), 150 stickies with text, 100 shapes, 50 text boxes, 30 connectors, 10 sections, 10 shot cards. It then
  measures, with requestAnimationFrame timestamps: a 3-second pan (wheel), a zoom from fit to 400% and back (Ctrl +
  wheel), a drag of 20 selected items, and a marquee over 200. Report the median and 95th-percentile frame time and
  dropped frames for each, before and after your changes, plus the time to open the board and memory (performance.
  memory in Chromium) after the zooms.
  - Budgets for the test: 95th-percentile frame under 33 ms for pans and zooms and under 50 ms for the drag, open
    under 3 s. The target is 16.7 ms (60 fps); say how far each gesture is from it.
- **Then make it fast, where the numbers say.** Likely places, only if the measurements point there:
  - drawing only items in view (5.0 has a first cut): make the culling cheap (a spatial index rebuilt per records
    version, not a scan of every item per frame);
  - layers: the board's static items on one Konva layer that is cached or not redrawn while only the view moves (move
    the Stage/Layer transform, don't rebuild nodes); the selection, handles, guides and drafts on a separate layer;
  - pictures (decision 4): the thumbnail while the drawn size × pixel ratio is at most 640, the full picture only up
    close (5.1b), decoded off the main thread (createImageBitmap) and never re-decoded on pan; during a fast zoom, keep
    the level already drawn until the gesture settles (about 150 ms) before switching;
  - text: measured once per text and style (5.1a's measurer is cached; check live cards and field cards too);
  - React: no re-render of every item node per pointermove (memoised nodes keyed on their geometry and props);
  - connectors: 5.2's memoised routing per end geometry (check it holds during pan, which moves no ends).
  - Don't change what anything looks like, nor any behaviour the e2e tests check. No new dependency.
- **A record of it** in docs/PLAN.md is the main session's; you report the numbers.
- **The two flaky tests** (each failed once or twice in full Chromium runs this phase and passed alone):
  - `e2e/player.spec.ts` › "the frame's clip plays in the inspector, in to out, round and round, only when asked
    (2.8)": a frame-timing check got 21 where it allows at most 20.
  - `e2e/boardMedia.spec.ts` › "zooming in past 640 screen pixels draws the stored picture; zooming out goes back to
    the thumbnail": its afterEach console check caught "Failed to load resource: net::ERR_CONNECTION_REFUSED".
  - Find each cause: for the first, whether the bound is too tight for a loaded machine or the playback really slips
    (fix the code if it slips, otherwise make the check measure what it means: frames shown inside the in–out range,
    not a count with no slack); for the second, which URL is refused (log the failing request's URL in the test's
    console check, run boardMedia.spec.ts and the full suite until it happens, or reason it out: a request to the dev
    server's old port, a revoked blob, an image loaded after the page closed) and fix the source. Never filter console
    errors to hide it, never weaken a test without saying exactly why the old bound was wrong.

## Checks to run

- `SB_PERF=1` (PowerShell: `$env:SB_PERF='1'`) `npx playwright test e2e/perf.spec.ts --project=chromium` before and
  after; then unset it.
- `npm run lint`
- `npm test` (includes `cargo test`), with Vitest and cargo counts.
- `npx playwright test --project=chromium`: alone, in the foreground (Bash timeout 600000; never let it go to the
  background, never wait on a background task), never two at once; then `npm run failed-tests`; report every failed
  or flaky test's name with the passed and failed counts, for every full run; a full run after your last change.
  Run the full suite three times at the end to show the two flakes are gone, and report each run.
