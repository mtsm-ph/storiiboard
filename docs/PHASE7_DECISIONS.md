# Phase 7 decisions (asked Nov 15, 2026; answered by Kevin, Nov 16)

One page. Each decision: the question, what is recommended and why, and how hard it is to change later. The plan is
in `docs/PLAN.md`, "Phase 7 milestones"; the scope is "AI assistant (MCP)" and "Phase 7 notes" there (Kevin, Nov 9),
"E · Desktop and web review", CLAUDE.md's MCP rules and the change-file format already in `docs/SBD_FORMAT.md`.
**Kevin has answered these. His by-hand passes no longer hold any phase (Kevin, Nov 18): he tests the alpha once,
thoroughly, when it is fully built, from docs/ALPHA_TEST.md. Phase 7 is built in the agreed order, each milestone
from its brief.**

| # | Question | Recommended | Change later |
|---|---|---|---|
| 1 | What is the MCP server written in, and how does it run? | **A Node program in `mcp/`** sharing src/core as it is (records, checks, the script parser, `nodeDriver` on Node's own SQLite, which was written for this). In Phase 7 it runs from the repo with the person's Node 22; packing it into the installers as one file is a Phase 8 item. The other way, in Rust inside the app, would mean writing the checks twice. | Medium. |
| 2 | **A dependency:** the official MCP SDK (`@modelcontextprotocol/sdk`, MIT, and the `zod` it needs), or the protocol by hand? | **The SDK**, pinned to a release at least two weeks old, used only in `mcp/`, never in the app. The protocol changes often; writing it by hand means following every revision ourselves. | Easy. |
| 3 | How does a proposal from the assistant reach the project while the app has it open? | **The assistant never writes the .sbd.** It opens the file read-only, and its proposals are written as a change file (`.sbdchanges`, `created_by: "mcp"`) into a `Suggestions/` folder beside the project, which the app brings in when the project is open or next opened. One way in for the web and the assistant, one writer for the file, and nothing a sync conflict can break. The other way (the server writing suggestion records itself) puts a second writer on a file the app holds open. | Hard: it is the trust boundary. |
| 4 | What can a suggestion do? The format has `trash`; `update`, `create`, `reorder`, `restore` and `comment` are reserved. | **Build `trash`, `update`, `create` and `reorder`** in format version 1 (its rule already lets kinds be added), each limited to a list in the code of record types and fields it may touch: frames, scenes, notes, a day's frames, order and gear list, a call sheet's notes and calls. Never people's contact details, never project settings, never files. `restore` and `comment` wait for the web (Phase 9). Each kind is written into SBD_FORMAT.md before it is built. | Hard: it is the file format. |
| 5 | Approving: strictly one by one, or groups? A script breakdown can be 200 suggestions. | **One by one stays the rule; each import is shown as a group** with its source, author and count, and the group offers **"Approve the rest" behind one confirmation that lists what will change**, only for kinds that add (never for deletions or for anything flagged as changed since). Reject all likewise. Every approval is its own op group, so each can be undone. | Easy. |
| 6 | "Cast called on a day they marked unavailable" has no data: availability arrives from the web in Phase 9. | **Add unavailable dates on the desktop now** (whole dates, in Cast and crew, per person), stored as `availability` records, the type the model already names, so Phase 9's web answers land in the same place. Then all seven checks run in Phase 7 and the gate can be met on a real shoot. Needs no new table. | Medium. |
| 7 | Where do the checks show in the app? | **A Checks tile** any workspace can open (in Production's default layout), running all seven over the whole project, each finding linking to its item; the call sheet's strip stays. The MCP's check tool returns the same list from the same function. The rain check uses only forecasts the project already holds: the server never fetches. | Easy. |
| 8 | The script tool needs the script, and import doesn't keep it. | **Keep the imported script in the project** as an asset (its text, at most 5 MB, as PDFs are kept), replaced when a revision is imported, with the earlier one in History. Then the assistant can read it, and a revised script can be compared with the last. A new kind of `media` record, no new table. | Medium. |
| 9 | Where does an approved breakdown (props, wardrobe, vehicles, stunts, VFX) live? | **Five lists on the scene**, plain lines of text, shown and editable in the scene's details and on its call sheet later. The assistant only ever suggests lines; a person can type them too. A record per item (so a prop could link to a day or a person) would be a new record type: not now. | Medium: lists can become records later. |
| 10 | Who does the thinking for the breakdown and smarter coverage? | **The assistant that called the server** (Claude Desktop, Claude Code, any MCP client). Storiiboard sends nothing anywhere and holds no key. **The optional in-app chat with the person's own key is left out of Phase 7**: it needs the keychain (a new Rust crate), four providers' hosts in net.rs and a chat screen. Propose it as its own phase after the release. | Easy. |
| 11 | Coverage from a script | **A plain rule, no AI:** "Suggest coverage" on a scene proposes a master, a medium and a single per speaking character (up to four) and one insert, as suggestions in the review screen, from templates in the code Kevin can reword. The assistant can propose its own through the same tools. | Easy. |
| 12 | Copy image prompt: what does it say? | **One English paragraph built from the frame's data in a fixed order** (shot size, lens, movement, INT/EXT and time of day, location, characters, action, the scene's palette as colour words and hex, aspect ratio), plus **a "look" line per project** (film stock, references, what to avoid) typed once in Project details. English whatever the app's language, since image tools read it best. A button on the frame and in its menu; works with no assistant. | Easy. |
| 13 | The "AI-generated image" mark | **A switch on the frame's picture** (it belongs to the picture, so it leaves when the picture is replaced), set by hand. A small "AI" tag on the board, in the storyboard PDF and as a column in the shot list CSV; not drawn into exported PNG frames, which are the pictures themselves. | Easy. |
| 14 | What may the assistant read? Whatever it reads goes to that assistant's maker. | **Everything except contact details by default**: phone numbers, emails and street addresses are left out of every read tool unless the project's switch "Let the assistant read contact details" is on (off by default, per project, in Settings → AI assistant, which also lists every tool and what it returns). Trashed items only when asked, as CLAUDE.md says. | Easy to loosen, hard to take back. |
| 15 | Transports | **stdio first** (Claude Desktop and Claude Code start the server themselves), then **local HTTP on 127.0.0.1** with the Origin check and a token made new each time it is switched on, shown once in Settings to copy. HTTP is off until switched on. | Easy. |
| 16 | **The tool list** (CLAUDE.md: ask before changing the MCP tools) | Read: `project_summary`, `list_scenes`, `list_shots`, `get_schedule`, `get_call_sheet`, `list_people`, `list_gear`, `list_locations`, `get_plan`, `list_suggestions`, `read_script`. Check: `run_checks`. Propose (each makes suggestions only): `suggest_shot_changes`, `suggest_new_shots`, `suggest_reorder`, `suggest_gear_for_day`, `suggest_call_sheet_notes`, `suggest_breakdown`, `suggest_trash`. | Medium: assistants learn the names. |
| 17 | A revised script | **In Phase 7, last:** importing a newer script proposes its changed, added and dropped scenes as suggestions in the review screen (PLAN.md has waited on this since Phase 1). A dropped scene is a suggested trash, never a deletion. | Easy to move to later. |

The gate (PLAN.md): the checks catch a real scheduling or gear mistake on Kevin's own material.
